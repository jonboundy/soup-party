# Data model

PostgreSQL, accessed through Prisma. The schema is `prisma/schema.prisma`; migrations are in `prisma/migrations`.

```
events          one row: the event's configuration

rsvps  1 ──── 0..1  soups  1 ──── 0..3  recipe_photos

host_sessions   the host's sign-ins
```

Tables and columns are `snake_case` in the database and mapped to `camelCase` in the Prisma client (`rsvps.attendee_name` is `rsvp.attendeeName`).

## Tables

### `events` (`Event`)

Event configuration. There is exactly one row, with `id` 1. The first migration inserts it with the title "Soup Party" and everything else empty.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `integer` | Primary key. Always 1. |
| `title` | `text` | Required. |
| `starts_at` | `timestamptz` | Null until the date is known. |
| `time_zone` | `text` | IANA zone used to display `starts_at`, e.g. `America/New_York`. |
| `location_label` | `text` | Nullable. |
| `address` | `text` | Nullable. May span several lines. |
| `map_url` | `text` | Nullable. Link to a map or directions. |
| `instructions` | `text` | Nullable. May span several lines. |
| `created_at`, `updated_at` | `timestamptz` | |

`starts_at` stores an instant, not a wall-clock time, so `time_zone` is what turns it back into "6:00 PM" for guests.

There is no foreign key from `rsvps` to `events`: with one event, every RSVP belongs to it.

### `rsvps` (`Rsvp`)

One row per response, from one guest or from two responding together.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key. Generated by the database. |
| `attendee_name` | `text` | Required. |
| `second_name` | `text` | The other half of a couple responding together. Null for one guest. Kept when the response is declined. |
| `status` | `rsvp_status` | `ATTENDING` or `DECLINED`. |
| `party_size` | `integer` | The guests named, while attending: 1, or 2 with a `second_name`. Null when declined. Never asked for: `src/lib/rsvp.ts` sets it from the names on every write. |
| `edit_token_hash` | `text` | Unique. SHA-256 hash of the private edit token, in hex. |
| `submission_hash` | `text` | Nullable for older RSVPs. Immutable SHA-256 fingerprint of the original validated creation payload; rejects conflicting retries. Never returned publicly. |
| `created_at`, `updated_at` | `timestamptz` | |

Only the hash of an edit token is stored. The raw token is issued privately in a fresh form and its confirmation/edit link; it must not be logged or returned from a public data endpoint.

New forms receive their private random token at request time. Its unique hash also serves as the creation idempotency key. A simultaneous insert waits on the unique constraint, then recovers the existing row; a retry must match its original `submission_hash`. Guest edits leave that fingerprint unchanged.

### `rsvp_rate_limits` (`RsvpRateLimit`)

Transient, shared abuse-control buckets: `key` (hashed client identity, primary key), `window_start` (timestamptz), and `attempts` (positive integer). A single PostgreSQL upsert increments or resets each 10-minute window atomically. `window_start` is indexed for removal of buckets inactive for more than a day. No raw IP addresses or guest credentials are stored here. See the README for deployment-specific identity and limits.

### `host_sessions` (`HostSession`)

One row per browser the host is signed in on. There is no host or user table: the host's only credential is the password hash in the `HOST_PASSWORD_HASH` environment variable.

| Column | Type | Notes |
| --- | --- | --- |
| `token_hash` | `text` | Primary key. HMAC-SHA-256 of the session token, keyed with the password hash, in hex. |
| `expires_at` | `timestamptz` | Indexed. Seven days after sign-in. A session past this is ignored. |
| `created_at` | `timestamptz` | |

The raw token exists only in the host's cookie. Signing out deletes the row. Rows that have expired are deleted at the next sign-in. Because the hash is keyed with the password hash, rows written under a previous password match nothing. See the README for the cookie and the authorization helpers.

### `soups` (`Soup`)

The soup a guest intends to bring. Optional: an RSVP with no soup row is a guest who has not decided.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key. Generated by the database. |
| `rsvp_id` | `uuid` | Unique. References `rsvps.id`. |
| `name` | `text` | Required. As the guest typed it. |
| `normalized_name` | `text` | Required. Indexed. Reduced form of `name` for duplicate detection, from `normalizeSoupName` in `src/lib/soup-name.ts`. |
| `recipe_url` | `text` | Nullable. Where the recipe can be found. Stored as a normalized `http(s)` address. |
| `recipe_text` | `text` | Nullable. The recipe written out. Line breaks are kept. |
| `created_at`, `updated_at` | `timestamptz` | |

A soup has a recipe when either recipe column is set or it has a photo. A recipe is public while its soup is active, at `/soups/<id>`, which makes the soup's `id` public for those soups. Both columns are written on every attending save, from what the form sent, so a form that leaves them out removes them. Photos are added and removed by requests of their own and are untouched by a save.

### `recipe_photos` (`RecipePhoto`)

Photos of a soup's recipe: a cookbook page, or a handwritten card. Part of the recipe, and public with it.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key. Generated by the database. Public, in the photo's address. |
| `soup_id` | `uuid` | References `soups.id`. |
| `position` | `smallint` | 0 to 2. Order on the recipe page. Unique within a soup. |
| `bytes` | `bytea` | A JPEG of at most 600,000 bytes, shrunk by the browser, with its metadata removed by the server. |
| `width`, `height` | `integer` | In pixels, read from the JPEG. At most 1,600 each. |
| `created_at` | `timestamptz` | |

A photo is never changed, only added or removed, so there is no `updated_at`. Select `bytes` only to serve a photo: lists of photos ask for ids and sizes. The limits are in `src/lib/recipe-photo.ts`, and the upload enforces them before the database does; changing them needs a migration for the constraints below.

## Relations

- **RSVP to soup is one to zero-or-one.** `soups.rsvp_id` is a foreign key with a unique index, so an RSVP has at most one soup. Dropping the unique index is all it takes to allow several later.
- **A soup cannot outlive its RSVP.** The foreign key is `ON DELETE CASCADE`: deleting an RSVP deletes its soup. Only the host's removal deletes an RSVP.
- **Soup to recipe photo is one to at most three.** `recipe_photos.soup_id` cascades on delete, so photos go with their soup, and so with its RSVP. The unique index on `(soup_id, position)` and the range of `position` together hold a soup to three.
- **Declining or cancelling does not delete the soup.** Guest cancellation sets the RSVP to `DECLINED` and clears `party_size`; the saved link remains usable. Clearing the soup name while attending deletes the soup row, and its recipe with it. Other guest edits update the RSVP and soup in one transaction. A soup is *active* only while its RSVP is `ATTENDING`. Anything that lists soups publicly must filter on that:

  ```ts
  db.soup.findMany({ where: { rsvp: { status: "ATTENDING" } } });
  ```

## Constraints

| Constraint | Table | Rule |
| --- | --- | --- |
| `events_singleton_check` | `events` | `id = 1`, so there is only ever one row. |
| `events_time_zone_check` | `events` | `time_zone` is required once `starts_at` is set. |
| `events_title_check` | `events` | `title` is not blank. |
| `events_map_url_check` | `events` | `map_url`, when set, starts with `http://` or `https://` and has no spaces. |
| `rsvps_attendee_name_check` | `rsvps` | `attendee_name` is not blank. |
| `rsvps_second_name_check` | `rsvps` | `second_name`, when set, is not blank. |
| `rsvps_party_size_check` | `rsvps` | Attending: `party_size` is 1 without a `second_name` and 2 with one. Declined: `party_size` is null. |
| `rsvps_edit_token_hash_key` | `rsvps` | `edit_token_hash` is unique. |
| `soups_rsvp_id_key` | `soups` | One soup per RSVP. |
| `soups_rsvp_id_fkey` | `soups` | `rsvp_id` references an RSVP; cascades on delete. |
| `soups_name_check` | `soups` | `name` is not blank. |
| `soups_recipe_url_check` | `soups` | `recipe_url`, when set, starts with `http://` or `https://` and has no spaces. |
| `soups_recipe_text_check` | `soups` | `recipe_text`, when set, is not blank. |
| `recipe_photos_soup_id_fkey` | `recipe_photos` | `soup_id` references a soup; cascades on delete. |
| `recipe_photos_soup_id_position_key` | `recipe_photos` | One photo per position per soup. |
| `recipe_photos_position_check` | `recipe_photos` | `position` is 0, 1 or 2. |
| `recipe_photos_bytes_check` | `recipe_photos` | `bytes` holds 1 to 600,000 bytes. |
| `recipe_photos_size_check` | `recipe_photos` | `width` and `height` are each 1 to 1,600. |

`normalized_name` is deliberately **not** unique. Similar soups produce a warning, never a rejection.

`normalized_name` is computed when the soup is written, so a change to `normalizeSoupName` does not reach existing rows. Recompute them in a migration alongside any such change.

These are the rules the database guarantees. Friendlier limits, such as maximum lengths, belong in request validation: see `src/lib/rsvp-schema.ts`.

Prisma's schema language has no syntax for `CHECK` constraints, so the `_check` rows above are hand-written SQL at the end of the migration that adds each. Prisma leaves them alone when generating later migrations.

## Timestamps and identifiers

- `created_at` and `updated_at` default to the current time in the database. The Prisma client sets `updated_at` on every update; an update made with raw SQL has to set it itself.
- RSVP, soup and photo ids are random (version 4) UUIDs from `gen_random_uuid()`, so they reveal nothing about order or count.

## Changing the schema

1. Edit `prisma/schema.prisma`.
2. Run `npm run db:migrate -- --name describe-the-change`. This writes a migration and applies it to the development database.
3. Run `npx prisma generate` to regenerate the client.
4. Commit the new directory under `prisma/migrations`.

To add a `CHECK` constraint or other hand-written SQL, pass `--create-only`, edit the generated `migration.sql`, then run `npm run db:migrate` again to apply it.

## Configuring the event

Edit the single `events` row, either in Prisma Studio (`npm run db:studio`) or with SQL. The values here are placeholders:

```sql
UPDATE events
SET starts_at = '2026-11-14 18:00 America/New_York',
    time_zone = 'America/New_York',
    location_label = 'The house',
    address = E'1 Example Street\nSpringfield',
    map_url = 'https://maps.example.com/?q=1+Example+Street',
    instructions = 'Bring a ladle.',
    updated_at = now()
WHERE id = 1;
```

The homepage's details section reads this row and shows the change within about a minute; no deploy is needed. Every column is optional. One that is null or blank is shown as "To be announced." rather than guessed at, and setting a column back to `NULL` restores that.

- The date and time both come from `starts_at`, displayed in `time_zone`. If `time_zone` is not a zone name the server recognizes, neither is shown.
- `map_url` adds a "Map and directions" link under the location.
- Line breaks in `address` and `instructions` are kept.
